Josha

Technologies and approaches behind Josha

Josha is a dual-pane, keyboard-driven file manager for Windows, built on .NET 9 and WPF. It aims at the same muscle memory as Total Commander — two panes, function-key operations, instant navigation — but adds first-class FTP/FTPS/SFTP sites, a disk-usage tree rendered on a virtualized canvas, and a background job queue for copies and transfers. This is a walkthrough of the parts of the codebase that make those features work, with links straight to the source.

One provider abstraction, three back ends

Every pane operation — enumerate, copy, move, rename, delete, open a stream — goes through IFileSystemProvider. The local file system, FTP/FTPS, and SFTP each implement it, so the pane view models never branch on which kind of site they're looking at. Business/IFileSystemProvider.cs#L18-L65

The interesting bit is ProviderId (L24). Local shares one identity across both panes; every remote site gets its own. When the file operation queue picks between a same-provider copy and a cross-provider import, it's just comparing that string: 

if (req.SrcProvider.ProviderId == req.DstProvider.ProviderId)
    return await req.DstProvider.CopyAsync(req.SrcPath, req.DstPath, progress, req.Overwrite, ct);
return await req.DstProvider.ImportFromAsync(req.SrcProvider, req.SrcPath, req.DstPath, progress, req.Overwrite, ct);

Services/FileOperationQueue.cs#L105-L111. That single check is what turns "drag a file from the left pane to the right pane" into either a local copy, an FTP upload, or an SFTP download, with no special-casing anywhere above it. Cross-provider moves reuse the same import path and only delete the source once the copy has actually succeeded, so a failed delete leaves a duplicate instead of losing data — L119-L126.

A provider also declares whether it SupportsTreeGraph (L28-L30) — the disk-usage view needs a full recursive snapshot, which only makes sense for local drives, so the pane simply greys out the shortcut for remote sites instead of the view model needing to know why.

FTP and SFTP: pooled connections, not one-shot clients

Remote sites are backed by FluentFTP for FTP/FTPS and SSH.NET for SFTP, both sitting behind a shared IRemoteClient interface (Business/Ftp/IRemoteClient.cs). Opening a control connection per operation would make every remote listing feel like a page load, so RemoteConnectionPool keeps up to MaxConnectionsPerSite live clients per site and recycles them across operations, closing a client only after it's sat idle for IdleSeconds: Business/Ftp/RemoteConnectionPool.cs#L16-L41.

The acquire/release pattern is an await using lease — if an operation fails with a connection-level fault, the caller marks the lease faulted so the pool disposes the client instead of handing a half-dead connection to the next caller. The file operation queue defaults to MaxConcurrent = 3 precisely because a single site's pool only holds 2 connections; that leaves room for a local copy to run alongside a remote transfer without starving either (Services/FileOperationQueue.cs#L10-L14).

Edit-on-server, without a per-file watcher

Pressing F4 on a remote file downloads it to a temp folder, launches the user's default editor, and uploads the result back on save. The tricky part is detecting "save" reliably: most editors don't write to the target file directly, they write a sibling temp file and rename it over the original, which a FileSystemWatcher scoped to the single file would miss entirely. EditOnServerWatcher instead watches the containing temp directory and listens for both Changed and Renamed→target events, debounces 400 ms because editors fire multiple events per save, and hashes the file before each upload so an editor's on-load "changed" burst or an unmodified save doesn't trigger a redundant upload: Services/EditOnServerWatcher.cs#L10-L22. The actual upload goes back through the same RemoteConnectionPool as every other transfer, so it isn't a special code path competing for connections.

Disk usage: an encrypted, incrementally-reconciled snapshot

The disk-usage tree needs a full recursive walk of a drive, which is too slow to redo on every open. Josha instead persists a tree snapshot per drive letter to josha_data\tree.<letter>.daps (Business/SnapshotComponent.cs#L24-L31), a flattened, indentation-delimited text format encoding each directory's name, size, child counts, and last-write time, then encrypts it with Windows DPAPI scoped to the current user before writing it to disk (L91-L104, Business/CryptoComponent.cs#L6-L18). Each caller supplies its own entropy value so one DPAPI-protected file can't be decrypted by unrelated code running as the same user, and because DPAPI keys are tied to the user profile and machine, a copied snapshot file is unreadable on another PC — it just gets rebuilt on the next scan instead of crashing (L127-L156).

Loading a snapshot is cheap, but trusting it blindly would show stale data. Reconciliation makes that fast by leaning on an NTFS guarantee: a directory's own last-write time changes whenever an entry is added, removed, or renamed directly inside it. So for a snapshot directory whose on-disk mtime still matches the cached one, Josha skips both FindFirstFileEx enumerations it would otherwise need and just recurses into children — a single GetFileAttributesEx syscall stands in for a full directory listing: Business/SnapshotComponent.cs#L393-L425. Only directories whose mtime actually changed fall through to the slower path that diffs the real child list against the cached one by name.

Reconciliation also parallelizes, but only at the top two levels of the tree (L514-L542), mirroring the same restraint in the initial scan: nesting Parallel.ForEach calls saturates the .NET thread pool faster than it can grow (roughly one new thread every 500 ms), which shows up as low CPU usage and a stalled UI rather than a fast scan — fanning out once at the root, with ~20-30 subdirectories under a typical C:\, already gives the scheduler plenty to chew on (Business/ScanCore.cs#L73-L95). The degree of parallelism is also capped at ProcessorCount - 1 so the dispatcher thread always keeps a core free for the loading-bar animation and UI bindings (L97-L110). The project also opts into server GC with concurrent collection in the csproj, specifically to absorb the high allocation rate of that parallel scan without the long gen-2 pauses workstation GC would cause.

Rendering a tree with hundreds of thousands of nodes

The disk-usage view is a custom TreeGraphControl that draws directly with WPF's DrawingContext rather than binding a TreeView to a huge item source — a drive with hundreds of thousands of files would make a real-control approach fall over. Instead, the control lays every visible node out into a flat array of rectangles once, then a binary search over that array finds the first and last node intersecting the current viewport on every scroll or zoom: Views/TreeGraphControl.xaml.cs#L353-L385.

Only that visible slice (plus a small buffer of 5 rows above and below, to absorb scroll momentum) gets real WPF elements on the canvas; anything that scrolls out is removed and its visual is reused if the same node scrolls back in (L387-L438). The connecting lines between nodes are drawn separately, once per frame, into a single shared DrawingVisual instead of one shape per edge (L452-L459), which keeps the visual tree small regardless of how deep or wide the expanded tree gets. Brushes and pens used for node chrome are all frozen at class-init time (L46-L67), which lets WPF share them across threads and skip change-notification overhead entirely.

The transfer queue: one Channel, N workers

Copies, moves, uploads, and downloads all funnel into FileOperationQueue, which is a thin wrapper around an unbounded System.Threading.Channels.Channel with a fixed pool of worker loops reading from it (Services/FileOperationQueue.cs#L19-L34). Enqueuing a job immediately adds a view model to an ObservableCollection so the queue panel updates the instant you drop a file, but that mutation is always dispatched onto the UI thread first — mutating an ObservableCollection off-thread is a reliable way to crash a bound ItemsControl (L36-L43). Completed and cancelled jobs clear themselves from the panel after a short delay; failed jobs stay until retried or dismissed, so a failure is never something you have to have caught in the moment to notice (L129-L143).

The stack, in one place

  • .NET 9 / WPF — net9.0-windows, server + concurrent GC, C# nullable reference types throughout.
  • FluentFTP and SSH.NET for FTP/FTPS and SFTP, unified behind one provider interface.
  • Vanara.PInvoke.Shell32 for native shell context-menu integration.
  • Windows DPAPI for at-rest encryption of snapshots and site credentials, with per-component entropy.
  • System.Threading.Channels for the background transfer queue, Parallel.ForEach (capped and shallow) for disk scanning.
  • Direct DrawingContext/DrawingVisual rendering with manual viewport virtualization for the disk-usage canvas.
  • A dedicated integration test project exercising the local, FTPS, and SFTP providers against real fixtures.
