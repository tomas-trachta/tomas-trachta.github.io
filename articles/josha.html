Josha

Technologies and approaches behind Josha

Josha is a dual-pane, keyboard-driven file manager for Windows, built on .NET 9 and WPF. It aims at the same muscle memory as Total Commander — two panes, function-key operations, instant navigation — but adds first-class FTP/FTPS/SFTP sites, a disk-usage tree rendered on a virtualized canvas, and a background job queue for copies and transfers. This is a walkthrough of the parts of the codebase that make those features work, with real snippets from the source (trimmed for length; // … marks an elision).

One provider abstraction, three back ends

Every pane operation — enumerate, copy, move, rename, delete, open a stream — goes through IFileSystemProvider, an interface with a ProviderId, a SupportsTreeGraph flag, and per-operation async methods (CopyAsync, MoveAsync, ImportFromAsync, …) that the local file system, FTP/FTPS, and SFTP each implement, so the pane view models never branch on which kind of site they're looking at. ProviderId is what makes cross-provider routing possible: local shares one identity across both panes, every remote site gets its own.

The local provider mostly just forwards to the existing static file-ops helpers, but ImportFromAsync is where the abstraction earns its keep: when the source is a different provider (an FTP download landing on local disk, say) there's no OS-level fast path, so it falls back to a manual read/write streaming loop instead:

Business/LocalFileSystemProvider.csview file →
public Task<FileOpsComponent.OpResult> ImportFromAsync(
    IFileSystemProvider src, string srcPath, string dstPath,
    IProgress<long>? bytesCopied, bool overwrite, CancellationToken ct)
{
    if (src is LocalFileSystemProvider)
        return CopyAsync(srcPath, dstPath, bytesCopied, overwrite, ct);

    return CrossProviderCopyAsync(src, srcPath, dstPath, bytesCopied, overwrite, ct);
}

private async Task<FileOpsComponent.OpResult> CrossProviderCopyAsync(
    IFileSystemProvider src, string srcPath, string dstPath,
    IProgress<long>? bytesCopied, bool overwrite, CancellationToken ct)
{
    try
    {
        if (File.Exists(dstPath) && !overwrite)
            return FileOpsComponent.OpResult.Fail($"Destination exists: {Path.GetFileName(dstPath)}");

        await using var srcStream = await src.OpenReadAsync(srcPath, ct).ConfigureAwait(false);
        await using var dstStream = await OpenWriteAsync(dstPath, overwrite, ct).ConfigureAwait(false);

        var buffer = new byte[1024 * 1024];
        long total = 0;
        int read;
        while ((read = await srcStream.ReadAsync(buffer.AsMemory(), ct).ConfigureAwait(false)) > 0)
        {
            await dstStream.WriteAsync(buffer.AsMemory(0, read), ct).ConfigureAwait(false);
            total += read;
            bytesCopied?.Report(total);
        }
        return FileOpsComponent.OpResult.Ok();
    }
    catch (OperationCanceledException) { return FileOpsComponent.OpResult.Cancelled(); }
    catch (Exception ex) { return FileOpsComponent.OpResult.Fail(ex.Message); }
}

When the file operation queue picks between a same-provider copy and a cross-provider import, it's just comparing that string:

Services/FileOperationQueue.csview file →
if (req.SrcProvider.ProviderId == req.DstProvider.ProviderId)
    return await req.DstProvider.CopyAsync(req.SrcPath, req.DstPath, progress, req.Overwrite, ct).ConfigureAwait(false);
return await req.DstProvider.ImportFromAsync(req.SrcProvider, req.SrcPath, req.DstPath, progress, req.Overwrite, ct).ConfigureAwait(false);

That single check is what turns "drag a file from the left pane to the right pane" into either a local copy, an FTP upload, or an SFTP download, with no special-casing anywhere above it. Cross-provider moves reuse the same import path and only delete the source once the copy has actually succeeded, so a failed delete leaves a duplicate instead of losing data:

Services/FileOperationQueue.csview file →
if (req.SrcProvider.ProviderId == req.DstProvider.ProviderId)
    return await req.DstProvider.MoveAsync(req.SrcPath, req.DstPath, progress, req.Overwrite, ct).ConfigureAwait(false);

// Cross-provider: copy first, delete source only on success.
// If the delete fails the file is duplicated, not lost.
var copy = await req.DstProvider.ImportFromAsync(req.SrcProvider, req.SrcPath, req.DstPath, progress, req.Overwrite, ct).ConfigureAwait(false);
if (!copy.Success) return copy;

var del = await req.SrcProvider.DeleteAsync(req.SrcPath, toRecycle: false, ct).ConfigureAwait(false);
if (!del.Success) return FileOpsComponent.OpResult.Fail($"Copied but couldn't remove source: {del.Error}");
return FileOpsComponent.OpResult.Ok();

FTP and SFTP: pooled connections, not one-shot clients

Remote sites are backed by FluentFTP for FTP/FTPS and SSH.NET for SFTP, both sitting behind a shared IRemoteClient interface. Opening a control connection per operation would make every remote listing feel like a page load, so RemoteConnectionPool keeps a small number of live clients per site and recycles them across operations:

Business/Ftp/RemoteConnectionPool.csview file →
public async Task<Lease> AcquireAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct).ConfigureAwait(false);
    try
    {
        IRemoteClient? client = TakeIdle();
        if (client == null)
        {
            client = CreateClient();
            await client.ConnectAsync(ct).ConfigureAwait(false);
        }
        Interlocked.Increment(ref _outstanding);
        return new Lease(this, client);
    }
    catch
    {
        _gate.Release();
        throw;
    }
}

A SemaphoreSlim sized to MaxConnectionsPerSite (2) caps concurrency, and an idle client is reused before a new connection is opened. Release puts the client back on an idle list guarded by its own cancellable eviction timer rather than disconnecting it immediately:

Business/Ftp/RemoteConnectionPool.csview file →
if (faulted || !client.IsConnected)
{
    await client.DisposeAsync().ConfigureAwait(false);
    return;
}

// CTS must exist before the entry is visible to TakeIdle —
// otherwise a parallel acquire pulls the entry while Cts is
// null, can't cancel the pending eviction, and the eviction
// later disposes a client the lease holder is still using.
var entry = new IdleEntry { Client = client };
entry.Cts = new CancellationTokenSource();
lock (_stateLock) _idle.Add(entry);

_ = Task.Delay(TimeSpan.FromSeconds(IdleSeconds), entry.Cts.Token)
    .ContinueWith(async _ => await EvictAsync(entry).ConfigureAwait(false),
        TaskContinuationOptions.OnlyOnRanToCompletion);

If an operation fails with a connection-level fault, the caller marks the lease faulted so the pool disposes the client instead of handing a half-dead connection to the next caller. The file operation queue defaults to MaxConcurrent = 3 precisely because a single site's pool only holds 2 connections; that leaves room for a local copy to run alongside a remote transfer without starving either.

Edit-on-server, without a per-file watcher

Pressing F4 on a remote file downloads it to a temp folder, launches the user's default editor, and uploads the result back on save. The tricky part is detecting "save" reliably: most editors don't write to the target file directly, they write a sibling temp file and rename it over the original, which a FileSystemWatcher scoped to the single file would miss entirely:

Services/EditOnServerWatcher.csview file →
_watcher = new FileSystemWatcher(tempDir)
{
    NotifyFilter = NotifyFilters.LastWrite
                 | NotifyFilters.FileName
                 | NotifyFilters.Size,
    EnableRaisingEvents = true,
};
_watcher.Changed += OnTempChanged;
_watcher.Renamed += OnTempRenamed;

// …

private void ScheduleUpload()
{
    _debounceCts?.Cancel();
    _debounceCts = new CancellationTokenSource();
    var token = _debounceCts.Token;
    _ = Task.Delay(TimeSpan.FromMilliseconds(400), token).ContinueWith(async t =>
    {
        if (t.IsCanceled) return;
        await TryUploadAsync().ConfigureAwait(false);
    }, TaskScheduler.Default);
}

Once the debounce timer fires, the file is hashed and compared against the hash of the last upload — an unmodified save or an editor's on-load Changed burst never reaches the network:

Services/EditOnServerWatcher.csview file →
string newHash = HashFile(_tempFile);
if (newHash == _lastUploadedHash) return;

await using var fs = new FileStream(_tempFile, FileMode.Open, FileAccess.Read, FileShare.ReadWrite,
    256 * 1024, useAsync: true);
await using var lease = await RemoteConnectionPool.AcquireAsync(_site, default).ConfigureAwait(false);
try
{
    await lease.Client.UploadAsync(fs, _remotePath, overwrite: true, resume: false, null, default).ConfigureAwait(false);
}
catch { lease.Faulted = true; throw; }

_lastUploadedHash = newHash;

The upload goes back through the same RemoteConnectionPool as every other transfer, so it isn't a special code path competing for connections.

Disk usage: an encrypted, incrementally-reconciled snapshot

The disk-usage tree needs a full recursive walk of a drive, which is too slow to redo on every open. Josha instead persists a tree snapshot per drive letter:

Business/SnapshotComponent.csview file →
private static string GetDataDir() =>
    DirectoryAnalyserComponent.WinRoot + "josha_data";

private static string GetSnapshotPath(string driveLetter)
{
    var letter = NormalizeDriveLetter(driveLetter);
    return Path.Combine(GetDataDir(), $"tree.{letter}.daps");
}

That's a flattened, indentation-delimited text format encoding each directory's name, size, child counts, and last-write time, then encrypted with Windows DPAPI scoped to the current user before it's written to disk:

Business/SnapshotComponent.csview file →
var sb = new StringBuilder();
WriteNode(sb, root, 0);

try
{
    var encrypted = CryptoComponent.ProtectString(sb.ToString(), DpapiEntropy);
    var wrapped = PersistenceMigrator.WrapV1(encrypted);
    FileAnalyserComponent.WriteFile(filePath, wrapped);
}
catch (Exception ex)
{
    Log.Error(LogCat, $"Failed to save {Path.GetFileName(filePath)}", ex);
}

Each caller of the underlying ProtectedData.Protect/Unprotect wrapper supplies its own entropy value so one DPAPI-protected file can't be decrypted by unrelated code running as the same user, and because DPAPI keys are tied to the user profile and machine, a copied snapshot file is unreadable on another PC. Loading catches that failure explicitly and isolates the file instead of crashing — the snapshot just gets rebuilt on the next scan:

Business/SnapshotComponent.csview file →
string text;
try
{
    text = CryptoComponent.UnprotectString(ciphertext, DpapiEntropy);
}
catch (Exception ex)
{
    Log.Error(LogCat, $"DPAPI unprotect failed for {Path.GetFileName(filePath)} (different user/machine?)", ex);
    BackupAndIsolate(filePath, "dpapi-failed");
    return null;
}

A few other corruption/version cases get the same treatment when unwrapping the file's envelope, before decryption is even attempted:

Business/SnapshotComponent.csview file →
switch (unwrap.Status)
{
    case PersistenceMigrator.UnwrapStatus.Ok:
        ciphertext = unwrap.Payload;
        break;

    case PersistenceMigrator.UnwrapStatus.NoEnvelope:
        // Pre-DPAPI snapshots were AES-HWID encrypted with no envelope.
        // Can't decrypt; isolate so the next save doesn't blow it away.
        // Snapshot will be rebuilt on next rescan.
        Log.Warn(LogCat, $"{Path.GetFileName(filePath)}: pre-DPAPI format; cannot read");
        BackupAndIsolate(filePath, "legacy-format");
        return null;

    // … NewerVersion / Truncated are handled the same way, each with its own reason string
}

Loading a snapshot is cheap, but trusting it blindly would show stale data. Reconciliation makes that fast by leaning on an NTFS guarantee: a directory's own last-write time changes whenever an entry is added, removed, or renamed directly inside it. So for a snapshot directory whose on-disk mtime still matches the cached one, Josha skips both FindFirstFileEx enumerations it would otherwise need and just recurses into children — a single GetFileAttributesEx syscall stands in for a full directory listing:

Business/SnapshotComponent.csview file →
// Ultra-fast path: directory mtime unchanged → no add/remove/rename happened
// at this level. NTFS bumps the parent dir's LastWriteTime on those operations,
// so an unchanged mtime is a strict superset of the old count+name heuristic.
// Single GetFileAttributesEx syscall; skips both FindFirstFileEx enumerations.
// Still recurses into subdirs so deeper changes are detected at their own level.
if (dir.LastWriteTimeUtcTicks != 0)
{
    if (!ScanCore.TryGetDirMtimeTicks(dir.Path, out actualTicks))
    {
        // … entry vanished since the snapshot was taken; clear it out
    }
    mtimeProbed = true;

    if (actualTicks == dir.LastWriteTimeUtcTicks)
    {
        dir.IsScanned = true;
        RecurseChildren(dir, ct, progress, level);
        return;
    }
}

Only directories whose mtime actually changed fall through to the slower path that diffs the real child list against the cached one by name. Reconciliation also parallelizes, but only at the top two levels of the tree, mirroring the same restraint in the initial scan:

Business/ScanCore.csview file →
// Only the top level fans out: nested Parallel.ForEach saturates the ThreadPool
// faster than it grows (~1 thread/500ms), which presents as low CPU + UI stalls.
// ~20-30 root subdirs of C:\ already give the top-level fan-out plenty to schedule.
internal static void RecurseIntoChildren(DirOD dir, CancellationToken ct, ScanProgress? progress, int level)
{
    if (dir.Subdirectories.Length == 0) return;

    if (level == 0 && dir.Subdirectories.Length > 1)
    {
        ParallelForEach(dir.Subdirectories, ct, sub =>
        {
            DeepScan(sub, ct, progress, level + 1);
        });
    }
    else
    {
        foreach (var sub in dir.Subdirectories)
        {
            if (ct.IsCancellationRequested) return;
            DeepScan(sub, ct, progress, level + 1);
        }
    }
}

internal static void ParallelForEach<T>(IEnumerable<T> source, CancellationToken ct, Action<T> body)
{
    // Cap workers at ProcessorCount-1 so the UI dispatcher always has at
    // least one core for the loading-bar Storyboard and binding updates.
    var po = new ParallelOptions
    {
        CancellationToken = ct,
        MaxDegreeOfParallelism = Math.Max(1, Environment.ProcessorCount - 1),
    };
    Parallel.ForEach(source, po, body);
}

The project also opts into server GC with concurrent collection in the csproj, specifically to absorb the high allocation rate of that parallel scan without the long gen-2 pauses workstation GC would cause.

Rendering a tree with hundreds of thousands of nodes

The disk-usage view is a custom TreeGraphControl that draws directly with WPF's DrawingContext rather than binding a TreeView to a huge item source — a drive with hundreds of thousands of files would make a real-control approach fall over. Instead, the control lays every visible node out into a flat array of rectangles once, then a binary search over that array finds the first and last node intersecting the current viewport on every scroll or zoom:

Views/TreeGraphControl.xaml.csview file →
// Binary search for the first index in _flatNodes whose node.Bottom > y.
private int LowerBound(double y)
{
    int lo = 0, hi = _flatNodes.Count;
    while (lo < hi)
    {
        int mid = (lo + hi) / 2;
        if (_rects[_flatNodes[mid]].Bottom <= y)
            lo = mid + 1;
        else
            hi = mid;
    }
    return lo;
}

// Binary search for the last index in _flatNodes whose node.Top < y.
private int UpperBound(double y)
{
    int lo = -1, hi = _flatNodes.Count - 1;
    while (lo < hi)
    {
        int mid = (lo + hi + 1) / 2;
        if (_rects[_flatNodes[mid]].Top >= y)
            hi = mid - 1;
        else
            lo = mid;
    }
    return lo;
}

Only that visible slice (plus a small buffer of rows above and below, to absorb scroll momentum) gets real WPF elements on the canvas; anything that scrolls out is removed and its visual is reused if the same node scrolls back in:

Views/TreeGraphControl.xaml.csview file →
private void UpdateView()
{
    if (_flatNodes.Count == 0) return;

    var viewRect = GetViewportCanvasRect();
    if (viewRect == Rect.Empty) return;

    double buffer = (NodeH + RowGap) * ViewBufferRows; // 5 rows
    int start = LowerBound(viewRect.Top - buffer);
    int end = UpperBound(viewRect.Bottom + buffer);

    // Build set of nodes that should be on canvas
    var shouldBeVisible = new HashSet<TreeItemViewModel>(end - start + 2);
    for (int i = start; i <= end && i < _flatNodes.Count; i++)
        shouldBeVisible.Add(_flatNodes[i]);

    // Remove elements for nodes no longer in viewport, add/reposition the rest …
}

The connecting lines between nodes are drawn separately, once per frame, into a single shared DrawingVisual instead of one shape per edge, which keeps the visual tree small regardless of how deep or wide the expanded tree gets. Brushes and pens used for node chrome are all frozen at class-init time, which lets WPF share them across threads and skip change-notification overhead entirely:

Views/TreeGraphControl.xaml.csview file →
static TreeGraphControl()
{
    TextBrush = Freeze(new SolidColorBrush(Color.FromRgb(0xE6, 0xED, 0xF3)));
    // … a dozen more frozen brushes for node/folder/file chrome …
    LinePen = new Pen(Freeze(new SolidColorBrush(Color.FromRgb(0x30, 0x36, 0x3D))), 1);
    LinePen.Freeze();
}

private static T Freeze<T>(T freezable) where T : Freezable
{
    freezable.Freeze();
    return freezable;
}

The transfer queue: one Channel, N workers

Copies, moves, uploads, and downloads all funnel into FileOperationQueue, which is a thin wrapper around an unbounded System.Threading.Channels.Channel with a fixed pool of worker loops reading from it:

Services/FileOperationQueue.csview file →
private readonly Channel<QueueJobViewModel> _channel =
    Channel.CreateUnbounded<QueueJobViewModel>(new UnboundedChannelOptions
    {
        SingleReader = false,
        SingleWriter = false,
    });

private bool _started;

public void Start()
{
    if (_started) return;
    _started = true;
    for (int i = 0; i < MaxConcurrent; i++)
        _ = Task.Run(WorkerLoopAsync);
}

Enqueuing a job immediately adds a view model to an ObservableCollection so the queue panel updates the instant you drop a file, but that mutation is always dispatched onto the UI thread first — mutating an ObservableCollection off-thread is a reliable way to crash a bound ItemsControl:

Services/FileOperationQueue.csview file →
public QueueJobViewModel Enqueue(FileOperationRequest request)
{
    var job = new QueueJobViewModel(request, RetryJob);
    // Mutating Jobs off the UI thread crashes bound views.
    DispatchInvoke(() => Jobs.Add(job));
    _channel.Writer.TryWrite(job);
    return job;
}

Completed and cancelled jobs clear themselves from the panel after a short delay; failed jobs stay until retried or dismissed, so a failure is never something you have to have caught in the moment to notice:

Services/FileOperationQueue.csview file →
// Failed jobs stay until retried or manually cleared so the failure
// remains actionable.
private void ScheduleClear(QueueJobViewModel job)
{
    if (job.Status == QueueJobStatus.Failed) return;

    _ = Task.Delay(TerminalLifetime).ContinueWith(_ =>
    {
        DispatchInvoke(() =>
        {
            if (job.Status != QueueJobStatus.Failed && !job.IsActive)
                Jobs.Remove(job);
        });
    });
}

The stack, in one place

  • .NET 9 / WPF — net9.0-windows, server + concurrent GC, C# nullable reference types throughout.
  • FluentFTP and SSH.NET for FTP/FTPS and SFTP, unified behind one provider interface.
  • Vanara.PInvoke.Shell32 for native shell context-menu integration.
  • Windows DPAPI for at-rest encryption of snapshots and site credentials, with per-component entropy.
  • System.Threading.Channels for the background transfer queue, Parallel.ForEach (capped and shallow) for disk scanning.
  • Direct DrawingContext/DrawingVisual rendering with manual viewport virtualization for the disk-usage canvas.
  • A dedicated integration test project exercising the local, FTPS, and SFTP providers against real fixtures.
